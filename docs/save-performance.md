# 从保存文件到游戏换绑的耗时

在 Steam《怪物猎人：崛起》16.0.2.0、REFramework c4b13148 上，对比上一份「18 类性能优化版」和本次增量热加载版。实机测试沿用同一个游戏进程、玩家原有 Mod 和 279 套装，关闭了 LooseFileLoader 的文件缓存。

## 文件修改后的实测

在村内选取正在播放的水车动作 `v01a00_suisha01.mot`。写入 A、用 B 覆盖同一路径、删除 B，游戏动作层的末帧依次由 239 变为 119、179，再恢复为 239。每个版本连续做三组，共九次，然后切回上一版再重复一轮。计时从写入关闭或删除完成开始，到默认监听器确认完成为止，包括 550 毫秒的文件写稳等待。

| 中位时间 | 上一版第一轮 | 本版第一轮 | 上一版第二轮 | 本版第二轮 |
| --- | ---: | ---: | ---: | ---: |
| 水车保存或删除到确认完成，每轮 9 次 | 2,077 ms | 1,043 ms | 2,069 ms | 1,043 ms |
| 连续查询游戏资源是否就绪，每轮 24 次 | 503.3 ms | 13.6 ms | 503.3 ms | 13.7 ms |

第二行测量游戏与监听器之间的单次往返。空闲时游戏每 250 毫秒检查通知。实际收到请求后，后续 0.5 秒内在每次游戏更新时检查通知，使已经就绪的步骤在下一帧继续。监听器先订阅回执，再发布带唯一编号的请求。回执写到一半或系统通知失效时，监听器仍会核对编号并补读。荒野版同样在帧更新中检查已就绪的任务。[荒野任务调度源码](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/e3ef3e067bfed2da5c1a1adac79c55fe1dbaaa08/src/hotreload.cpp#L3199)

## 目录和引用关系

荒野版记录有改动的文件，并复用同一帧已经解析的路径。崛起沿用了这个做法，保存引用的正向和反向关系。改贴图内容时可直接查到使用它的资源。修改 UVS 或 EFX 内的引用时，只更新对应的引用，并用提交前后的两份索引找受影响的资源。同一批游戏组件的查询结果只在该次同步发现过程中复用。玩家重建或随后换绑时会重新查询。[荒野引用索引](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/e3ef3e067bfed2da5c1a1adac79c55fe1dbaaa08/src/references.cpp#L115) · [荒野同帧路径复用](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/e3ef3e067bfed2da5c1a1adac79c55fe1dbaaa08/src/hotreload.cpp#L3303)

在临时 NTFS 目录生成 4,000 份引用文件和 1 份贴图。分别改变贴图的版本标记和一个引用文件的实际内容，每种重复 21 次，逐次核对新旧版给出的依赖、别名和受影响路径。另在有 2,000 个文件的目录中连续三批各添加 96 个文件，单独计时 Windows 发出通知后的快照更新。该测试计时止于监听器，游戏加载另用上面的水车计时。

| 监听器内计时项目 | 上一版中位时间 | 本版中位时间 |
| --- | ---: | ---: |
| 本机 105 个原有松散文件，改变一张贴图的版本标记，更新并查询依赖 | 0.324 ms | 0.006 ms |
| 4,001 个测试文件，同样的贴图操作 | 166.78 ms | 0.42 ms |
| 4,001 个测试文件，实际改写一个引用，再更新并查询依赖 | 167.75 ms | 1.17 ms |
| 2,000 个起始文件，每批新增 96 个，识别并更新快照 | 3,830 ms | 6.84 ms |

## 不改文件时的帧时间

先完成翔虫 HUD 的同路径替换和删除，再让猎人在村里往返。训练场测试回放同一套移动和弓攻击输入。每次回放持续 54 秒，取其中 45 秒的 DXGI Present 帧间隔。实际行程分别为 225 米和 223 米，训练场记录到 34 次攻击输入和六个动作编号。

| 场景 | 上一版 P99 | 本版 P99 | 本版最长帧 | 本版超过 12 ms 的帧数 |
| --- | ---: | ---: | ---: | ---: |
| 村内往返，翔虫 HUD 已换绑 | 6.856 ms | 6.818 ms | 8.028 ms | 0 / 8,076 |
| 训练场移动并出弓 | 7.294 ms | 7.293 ms | 8.028 ms | 0 / 7,718 |

两段采样中，外部监听器的读取次数和其他 I/O 操作次数均为零，Windows CPU 时间计数均未增长。两版在这些路段的帧时间接近，大型怪物实战的抽帧仍缺同场景数据。[上一版的帧时间和测试方法](performance.md)

### 装备预览尚未打开

在村内添加再删除装备预览的 RTEX，会留下一个等待界面打开的 UVS。旧的等待方式在 12 秒内发出 9 次就绪查询。本版在相同的 12 秒内发出 0 次。让游戏加载原版装备预览 `preview_obj.gui` 后，界面发出就绪通知，监听器将两个实际节点绑定到当前 UVS。游戏重载脚本也会发出通知，让尚在等待的监听器重新登记。持续等待时每 60 秒续订一次，目录通知不可用时使用原有的定时查询。

在装备预览一直关闭的情况下另采样一次村内往返。45 秒内记录 8,141 帧，P99 为 6.866 ms，最长为 7.714 ms。独立监听器读操作为 0，其他 I/O 操作为 1。同样让预览保持关闭，再测九次水车保存与删除。在只优化引用索引和请求调度的中间版本上，中位时间为 2.054 秒。加入界面就绪通知并缩短并发请求等待锁的重试间隔后，中位时间为 1.042 秒。

## 实机换绑检查

- **279 外观**。同编号替换、切换 265 再切回、直接重建和删除回退均通过。实际手甲材质槽依次为 A 套 6 个、B 套 3 个、原版 2 个。放回 A 套后恢复 6 槽，13 份文件逐一通过 SHA-256 核对。
- **特效依赖**。让运行中的 `effect_player00` 使用测试 UVS，先保存其引用的贴图 A，确认特效资源更新。把 UVS 改指贴图 B 后再次保存 A，运行中的特效资源地址保持一致。保存 B 后地址变化，换回原件后仍有 4 个任务和 4 个发射器。
- **翔虫 HUD**。REFramework 可将同一种界面数组暴露为普通托管对象。本版在查询所在的游戏回调中取出节点，供后续分帧处理。图标 A、同路径 B 和删除回原版三个阶段，每次由村内去训练场再返回，均有 14 个节点绑定当前资源。
- **预制体**。`ItemTake` 的同路径工厂重建样本依次生成原版 `ItemTake`、A 的 `epvs_0004_ec010_00_0000`、B 的 `hm12_001` 和删除后的 `ItemTake`，各阶段从生成对象读取根节点名。

本次也用原版、A、同路径 B、删除回原版的顺序复测了 JCNS、MOTBANK、MOTLIST、UVAR、FBXSKEL、RCOL、GUI 和 USER。约束目标数为 4 → 3 → 2 → 4，碰撞球半径为 2.3 → 2.625 → 2.875 → 2.3，相机插值时长为 60 → 24 → 48 → 60。MMTR 和 RTEX 在本轮核对了 A、B 文件实际被游戏打开以及删除后取得新资源。此前逐像素核对的结果收录在[18 类资源验收](reentry-18.md)。
