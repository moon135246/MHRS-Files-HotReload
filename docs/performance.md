# 不改文件时的帧时间

Steam 崛起 16.0.2.0、REFramework c4b13148。旧版是上一份「18 类同路径热加载」发行包。两版在同一个游戏进程里交替运行，使用原有 Mod、同一身 279 装备和相同游戏设置。监听目录中有 105 个受支持的松散文件，LooseFileLoader 的文件缓存关闭。每一段计时期间都没有改动松散文件。

## 移动和出招

| 场景 | 版本 | 平均 FPS | P99 帧间隔 | 最长帧间隔 | 超过 12 毫秒的帧 |
| --- | --- | ---: | ---: | ---: | ---: |
| 村内往返 | 旧版 | 180.85 | 6.885 ms | 7.612 ms | 0 |
| 村内往返 | 优化版 | 181.08 | 6.826 ms | 7.632 ms | 0 |
| 翔虫 HUD 重新绑定后，在村内往返 | 旧版 | 181.04 | 6.776 ms | 7.520 ms | 0 |
| 翔虫 HUD 重新绑定后，在村内往返 | 优化版 | 179.78 | 6.856 ms | 7.742 ms | 0 |
| 训练场弓手移动并出招 | 旧版 | 171.29 | 7.210 ms | 7.997 ms | 0 |
| 训练场弓手移动并出招 | 优化版 | 171.04 | 7.294 ms | 8.039 ms | 0 |

测试脚本向本地猎人的输入对象回放相同的左摇杆输入，训练场另加入 34 次攻击按键。每轮输入持续 54 秒，通过猎人坐标确认村内实际行程约 225 米、训练场约 224 米。两版训练场均读到了拔弓状态和六个动作编号。计时开始前完成移动或出招预热。HUD 场景先对游戏自带的翔虫 UVS 做一次原路径重新绑定，让 14 个实际绑定进入后续维护。

表中每行取 45 秒 Windows DXGI ETW 数据，按游戏进程的主交换链统计相邻 Present 开始事件的时间差，并排除测试提交。P99 表示 99% 的帧间隔低于该数值。三组对照的帧时间相近，均未复现玩家反馈的周期性长帧。大型怪物狩猎尚缺同场景采样。

## 监听器的开销

| 同一批 45 秒采样 | 旧版 CPU 时间 | 优化版 CPU 时间 | 旧版其他 I/O 操作 | 优化版其他 I/O 操作 |
| --- | ---: | ---: | ---: | ---: |
| 村内往返 | 1.547 s | 0.000 s | 212,768 | 0 |
| HUD 重新绑定后往返 | 1.891 s | 0.000 s | 212,768 | 0 |
| 训练场弓手移动并出招 | 1.813 s | 0.000 s | 213,744 | 0 |

这些是独立 Python 监听进程的 Windows 计数器差值。其他 I/O 操作取自 `OtherOperationCount`，包括目录与文件元数据操作。CPU 时间的零值表示该采样窗口内计数器没有增长。

原监听器大约每 0.2 秒扫描一次目录。新版在启动时建立快照，随后等待 Windows 的目录通知，只检查发生变化的路径。整目录移入、改名或移出时更新对应子树。系统报告丢失事件时，监听器重新核对完整快照。一次复制中的关联资源继续使用原有的稳定等待、写入者检查和整批提交。后台等待通知的做法借鉴了本地荒野版。[荒野参考源文件](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/e3ef3e067bfed2da5c1a1adac79c55fe1dbaaa08/src/file_watcher.cpp)

游戏端的 Windows 通知单独过滤 `request.json`。旧版会定期在 UpdateBehavior 中读取这个文件，新版在通知到来后读取。另用 NTFS 文件打开观察器检查了四秒空闲窗口，新版没有重新打开该文件。维护预制体时每帧最多检查八条记录，退休资源仍由活实例持有。界面重新创建后对 UVS 的检查也分帧，每次最多筛查八个界面组件，或在已匹配的视图中处理 24 个纹理节点。

## 热加载回归

| 对象 | 优化版实测 |
| --- | --- |
| 穿在猎人身上的 279 | Meira A 套带有 6 个手甲材质槽。同编号 B 套覆盖后出现 3 个指定槽，删除后恢复游戏原版的 `Arm` 和 `Hand`，放回 A 后恢复 6 个槽。切到 265 再切回、直接重建玩家，两种方式均通过。回到村里后角色正常绘制，A 套 13 份文件的 SHA-256 全部与测试前一致。 |
| 翔虫 HUD | A、B 和删除回退三个阶段分别进入训练场再回村。每次检查的 14 个活动 UVS 绑定全部指向预期资源，延迟发现流程也找到了重新就绪的 HUD。 |
| ItemTake 预制体 | 实际创建的根对象依次为 `ItemTake`、`epvs_0004_ec010_00_0000`、`hm12_001`、`ItemTake`。 |

Windows 自动测试 13 项通过。文件通知测试覆盖全部 18 类的所有受支持后缀，包括一批文件同时新增、保留大小与时间戳原地覆盖、同时删除、整目录移入移出和通知丢失后的重新核对。各格式的引擎内完整验收记录来自上一版。[18 类逐项验收](reentry-18.md)
