# 荒野功能对照与崛起冷路径实测

本文的 `local-tests/` 链接指向开发机保存的原始回执。各项实测读数已列在正文中。

## 1.1.0 源码对照

对照本工作区的荒野 v1.0.1。荒野按逻辑路径合并保存事件，向引擎请求新资源，枚举实际引用者，并在依赖就绪后更新它们。崛起版这次调整了从文件落盘到场景提交的三个环节。

| 环节 | 1.0.9 中找到的差异 | 1.1.0 的行为 |
| --- | --- | --- |
| 同时保存多个资源 | 整批共享稳定期和重试；单文件才尝试直接换绑普通组件。一次复制多个互不相关的文件，现用组件可能要等下次创建。 | 按旧、新和 PAK 的引用关系分组，共用装备挂点的部件仍一起提交。其他组独立等待和重试。准备期间使用者发生变化，会重新发现。 |
| MDF 等待依赖 | 已有缺失模板的等待机制，但原生读数没有报告未就绪 TEX 的逻辑路径。 | 从正在加载的 MDF 获取所等的 MMTR 或 TEX。已确定缺失的路径补齐后唤醒相关组。普通和平台 MMTR 都会触发模板刷新。 |
| 玩家装备 | 单件装配失败和特定脚本恢复仍可转入整人重建。武器对象就绪、全局输入和训练场区域号也能影响防具提交。 | 按本地根对象、实际防具、装备索引和部件工厂就绪推进。场景交接时只传逻辑路径，在新猎人身上重认实际穿戴者。正常换装和当版脚本恢复都在原猎人上进行。对旧版遗留的同进程恢复记录仍保留收尾处理。 |

### 18 类资源的对照范围

| 格式 | 崛起当前如何更新 | 采用或保留的依据 |
| --- | --- | --- |
| MESH、MDF2、TEX、MMTR | 查询现有渲染器与材质引用。单独改材质可以留在原渲染器，带新骨架和活动物理的外观在原猎人挂点装配。 | 荒野的 `refresh_meshes` 与材质依赖重试。崛起曾在换模型后留下旧末端骨和活动 CHAIN，因此保留对局部骨骼、材质槽和活动组的回读。[骨架实测](worn-skeletons.md) |

| FBXSKEL、CHAIN、JCNS、RCOL | 通过实际骨架、物理或约束持有器更新，在相应组件读回变换、活动组、目标数或形状。 | 崛起使用 CHAIN.48。活动 CHAIN 依赖已穿防具的末端关节；RCOL 旧持有器的回切曾发生游戏退出。样例和保留旧引用的依据见[同路径实测](reentry-18.md)。 |
| PFB、USER、GUI | 重新请求同路径资源、更新工厂和可映射的存活实例。新建实例可读取完整新资源。 | 对应荒野的预制体级联、用户数据与视图刷新。崛起结构不同的 PFB 曾在回退创建时退出。已有实例的任意层级增删、嵌套 USER 原地改写和 GUI 任意结构修改尚未证明与荒野等价；已有工厂重入和重新创建视图分别有实测。 |

## 1.0.7：持武器时的刷新

荒野的 `HotReload::refresh_meshes` 枚举当前场景的 Mesh，匹配正在使用的资源再换绑。`mdf2_pending_deps` 和依赖重试处理尚未就绪的材质。这里没有统一的收刀判断，也不能由此推断所有资源在任意帧都能立即替换。

| 检查的路径 | 崛起 1.0.7 的处理 |
| --- | --- |
| 穿在身上的防具 | 身份、装备索引和当前部件匹配即可开始。可直接换绑的单件顶点编辑更新原渲染器；结构或骨架改变时在原猎人挂点装配，核实新件的材质和活动 CHAIN 后才退掉旧件。拔刀、瞄准、移动、转身、体力和耐力变化不参与这两条路径的就绪判断。 |
| 文件监听与材质依赖 | 同路径资源继续使用崛起自己的平台文件与 PAK 回退；删除了准备整套文件前专为采样站姿而发的一次游戏请求。渲染器仍等待实际依赖。 |
| 贴图、材质、动作、特效、GUI 和相容的单独 CHAIN | 检查了资源分派入口：这些路径依据各自的使用组件、材质依赖、播放器或视图状态刷新，没有共用防具的收刀判断。此轮没有重测 18 种格式。 |
| 仍要推迟的情况 | 场景交接、装备归属或资源代次改变、界面禁用全部输入、共享工厂尚未就绪，不能直接提交旧请求。只有实际调用 `reloadPlayerModel` 的部分装备兼容或脚本重置恢复流程才另行确认可操作、收刀、站稳，再采样需要保留的状态。 |

**实机只用一种武器。** 单人训练场、原装 Lua Bone System、明月的第 215 格弓。持弓从原版装梅、切天狐、卸载回原版。首轮安装缺少外观所用的 Moon 材质模板；7,242 帧保持拔弓但没有换装。补齐模板后，不收刀、不再复制防具文件，原来的请求自动完成。三段成功采样依次为 **2,004/2,004、801/801、652/652 帧持弓**，隐藏帧均为零。天狐替换和卸载从最后落盘到资源可见分别为 3.28 和 2.54 秒。三个阶段的猎人、弓身、箭囊和材质控制器地址都与基线相同；手甲活动 CHAIN 为 2 → 15 → 16 → 2。卸载后染色与基线一致。

## 荒野 v1.0.1 实机对照（2026-11-16）

在 Steam Build 25921695、REFramework c4b13148 上安装作者发布的 `file_hotreload.dll`。启动前移出女 003 外观的 84 个模型、材质、贴图及配套文件。选择存档和进入营地后均看到原版紫色羽甲。在营地保持同一名猎人和同一镜头，逐文件恢复覆盖后，模型轮廓先改变，材质短暂呈黑色。约 14 秒后，长卷发、黑白衣料和刺绣均出现。恢复的 84 个文件逐一通过 SHA-256 校验。[v1.0.1 发布与源码](https://github.com/AleksKavil/MHWS-Files-HotReload/releases/tag/v1.0.1)

从源码和这一局的日志可对应到四个步骤。

1. DLL 内的目录监听线程递归接收新增、写入和重命名后的文件名。文件大小和写入时间稳定且可打开后，游戏回调才消费这批变化。
2. 对已登记的松散路径，加载时重新核对磁盘是否有文件。即使框架在启动时记住了某条路径不存在，后加入的覆盖也能被选中。游戏尚未请求的资源等下次正常读取。现场保存的 034 胸甲就走了这条路径。
3. 对已经在用的路径，引擎重新请求资源。003 胸甲首次加载时，部分贴图仍在准备。16:07:20 日志记下依赖重试，随后有 44 项材质依赖就绪，一个现存 Mesh 切到新材质。
4. 插件同时更新仍引用旧资源的预制体，保障之后创建的装备也能使用更新。网格已经换上、材质仍在等待的中间画面，需要与全部依赖就绪后的画面分别核对。[目录监听](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/v1.0.1/src/file_watcher.cpp) · [游戏侧重载](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/v1.0.1/src/hotreload.cpp)

v1.0.1 的目录监听器只将新增、修改和新名称排队。单独删除文件能否让正在显示的对象立即回到 PAK，须作为另一个用例验收。

## 崛起的整包对照（2026-11-16）

### 早期玩家包的冷加载实机验收

使用 Steam Build 17920865、原版 REFramework c4b13148，启用 LooseFileLoader 和默认文件缓存。插件与游戏的 PID 同为 3008。启动前两份压缩包各自的原生资源和配套 JSON 均未安装，公共贴图和材质模板共 8 个文件原本已经存在。进入村庄后固定镜头，将原包的游戏文件写入对应目录，逐文件核对内容。每一步均等待游戏回执，随后拍摄当前猎人。此轮测试的是磁盘安装后的游戏行为。

| 桥头同一猎人 | 包内游戏文件 | 手、腰、头、身、腿材质槽 | 头部 FullBody / HairShapeData[58][2] |
| --- | --- | --- | --- |
| 启动时的原版红披风 | 两包均未安装 | 2 / 1 / 1 / 1 / 1 | false / 0.75 |
| 首次安装「梅」，紫色长发和黑白绣纹出现 | 97 个原生资源、7 份 JSON | 6 / 31 / 21 / 1 / 1 | true / 0 |

| 卸载后原版披风恢复 | 两包均已移除 | 2 / 1 / 1 / 1 / 1 | false / 0.75 |

四次采样的五个 Mesh 组件地址逐一相同，均报告材质就绪。卸载后，插件临时创建的文件名以 `.stm` 结尾的文件已归零。已有的手、身、头、腰四处 CHAIN 在此轮原地切换中维持原来组数 2 / 1 / 1 / 2。整套装备的物理按游戏创建部件的时机更新。配套 JSON 已按两份外观原包放置并还原，其消费时机由 LUABoneSystem 和 ArmorVariantManager 决定。

整包测试还复现了一处头部回退故障。当猎人正在使用天狐时，卸载产生的新头部 USER 可能已经有托管对象，但脸或头发数组仍在反序列化。最终版从崛起 PAK 读取原版的 498 项头部字段，对当前可用的实例恢复数值，并对正在初始化的字段限时重试。梅与天狐的头部 USER 文件内容相同，与原版相差六个字段。

本机的四张截图为 `local-tests/cold-install-20261116/rise-release-{stock,mei,fox,restored}.jpg`，对应的实机回执为 `rise-bindings-release-*.json`、`rise-extra-release-*.json`，完整监听日志为 `rise-release-cold.log`。

### 启动前已经装好自定义骨架的反向测试

同一份玩家 DLL（SHA-256 `94940af5fd892d309694171d060359f07c7ae390595544d6f66825fb8228c037`），新进程 PID 21332。在启动前放入梅的 97 个原生资源及 7 份 JSON，监听基线为 105 个原生文件。进村时五个部件材质槽为 6 / 31 / 21 / 1 / 1，手、身、头、腰的 CHAIN 组数为 15 / 1 / 23 / 8，头部抽样为 true / 0。

在村内卸载整包后，当前猎人仍穿梅。日志列出保留的五组模型和材质，12 份供后续装备创建的临时平台文件逐字节匹配游戏当前 PAK。静止时没有强行替换这个带自定义骨架的角色。通过游戏正常的村庄地图移动接口进入训练场后，五个部件都换成了新组件，槽数恢复为 2 / 1 / 1 / 1 / 1，四处 CHAIN 恢复为 2 / 1 / 1 / 2，头部恢复为 false / 0.75。训练场画面可见原版白发、红披风和背上的弓。正常返回村庄后再次取样，原版画面、槽数和物理均保持。两次区域移动均在 PID 21332 中完成。

训练场移动由临时验收脚本调用游戏的 `snow.VillageAreaManager.fastTravel`，未调整装备选择。玩家包不含该脚本。本机保留了 `rise-release-preinstalled.jpg`、`rise-release-reentry-training.jpg`、`rise-release-reentry-village.jpg`，以及各阶段的材质、物理和头部实例读数。

退出本轮游戏后，12 份 PAK 回退文件仍在磁盘。移除地图验收脚本并从 Steam 正常再启动一次，插件自动将这 12 份清零，随后记录 `Watching 8 loose files`。两套测试外观及其 7 条 JSON 路径均已恢复到测试前状态。

在相同宿主上，普通路径曾在梅的材质文件已经写入后仍返回原版的 `Arm / Hand`。另一次在模型组件保持原状的对照，把腰甲 MDF 作为手甲的平台文件交给游戏：用平台路径请求手甲后，同一逻辑资源的贴图引用由手甲 ALBD 改成腰甲 ALBD；回滚又恢复手甲 ALBD。崛起版据此可在原版 REFramework 上给出同路径的新一代资源。游戏只在依赖准备好、材质槽与磁盘一致后才更新现存 Mesh。

### 尚缺的格式和行为

本地 `MHR_STM_Release.list` 中没有找到 EFCSV、HTEX、CLSP、GPUC、SFUR、ABCMESH 的同名资源。清单包括带平台后缀的条目。没有崛起样本可用于这六项的原生消费者和冷加载验证。即使同为 RE Engine，也不能把荒野文件直接作为通过样本。

上表记录首次冷加载实验。当时的 GUI、PFB 和 USER 字段限制适用于原地写入已存在的实例。后续版本增加了整份资源重新创建、常驻预制体工厂重新就绪、停用组件恢复及材质运行时值合并。279 的两种重入方式、GUI 树、预制体子对象、嵌套 USER 引用和 18 类样本的结果另见[同路径替换与删除回退验收](reentry-18.md)。

### 复现早期 18 类随机路径开发实验

以下步骤对应当时的独立 Python 监听器和随机路径探针。`Enable file cache` 的关闭操作用于复现早期的 EFX → UVS 对照。1.0.1 玩家包使用 DLL 内的监听器，安装与使用步骤见 [README](../README.md)。

1. 游戏内启用 LooseFileLoader。测试启动后才新增的松散覆盖时，在 `LooseFileLoader → Debug` 暂时关闭 `Enable file cache`。村内玩家 EFX 实测在开关启用时返回过绑定回执，却没有打开新的 UVS；关闭后以另一条全新路径重新测得首次打开。
2. 启动 `tools/watch_outfit.py`，用 `python -u` 运行并将标准输出重定向到文件。GUI、PFB 和 USER 可用 `--baseline-root "<同游戏版本的原版 natives/stm>"` 在第一次保存时计算差异。通用单根 USER 另加 `--rsz-schema "<rszmhrise.json>"`。
3. 可在 REFramework 的 ScriptRunner 中运行 `tools/cold_component_probe.lua`，再执行下面的命令。原件与改件均由测试者提供。工具生成唯一逻辑路径，验证同一组件的首次绑定、替换与恢复，输出 JSON 并销毁临时实例。该命令覆盖六种直接绑定的格式；手甲的独立文件打开观测使用 README 中的 `test_cold_arm279.py`。

```powershell
python tools/test_cold_component.py "<游戏目录>" "<监听日志>" chain "<原件.chain.48>" "<改件.chain.48>"
```
