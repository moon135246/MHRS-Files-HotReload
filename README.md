# MHRS-Files-HotReload 1.1.0

《怪物猎人：崛起》松散资源热加载工具。在村庄、训练场和进行中的任务里，安装当前穿戴装备的外观、换成另一套或卸载，插件会更新本地猎人。训练场及进行中的任务里，拔刀、瞄准、移动和耐力变化不再推迟原猎人身上的防具刷新。玩家包只有一个 DLL，可搭配原版 Lua Bone System 或 FirstNatives。各类贴图、材质、模型、动作等共 18 类资源的刷新时机见下表。实测环境为 Steam 16.0.2.0、Build 17920865、REFramework c4b13148。

本项目在开发过程中借鉴了 Stellar 的《怪物猎人：荒野》热加载工具，尤其是文件监听、同路径资源重载和场景刷新。感谢作者公开实现，供崛起版开发时对照。[荒野热加载项目](https://github.com/AleksKavil/MHWS-Files-HotReload) · [致谢](#致谢)

## 安装与实测范围

1.1.0 用当前猎人、已登记的防具和资源依赖判断何时刷新。部分防具、整套以及脚本重置后的装配恢复都走原猎人挂点。换场收到的部分防具变更也能按新猎人的实穿路径重试。一次复制多个资源时，按使用者分组，已就绪的组件可以先更新。具体格式、保留差异及实测范围见[荒野源码对照](docs/wilds-parity.md)。

1.0.9 按当前猎人和实际防具挂点判断原位换装。部分任务的开场演出标志在正式狩猎时仍为真，现可在这类任务中刷新。场景切换期间收到整套文件变更时，插件等待新猎人的五件挂点，重新核对所穿资源，再使用新场景的挂点装配。

1.0.8 沿用荒野处理缺失材质依赖的方式。穿戴装备的 MDF 等待自定义 MMTR 超时，且对应模板在松散目录与游戏 PAK 中都找不到时，监听日志会输出 `Missing MMTR` 和所缺文件的路径。装入对应材质前置，或更换、卸载这套外观，插件会重新处理这次换装。等待期间，单独保存的其他资源仍可刷新。「梅」「天狐」使用的 Moon 模板来自单独的 Moon_Rise 前置。

1.0.7 在原猎人装配和单件顶点换绑之前检查场景、装备身份与资源就绪。该版本曾对界面输入和整名猎人重建设置额外条件。1.1.0 已移除这两个入口限制。

1.0.6 使用猎人当前装备请求选择游戏自己的防具预制体，把新部件装到原猎人的 Transform 下。游戏登记新件后，插件核对材质、局部关节和活动 CHAIN，再让旧件退场。收刀站稳后可以直接装梅、切天狐或卸载，武器和箭囊保留在身上。首次安装也可以在游戏启动后进行。[原猎人挂点的实机验收](docs/worn-skeletons.md#原猎人的五个防具挂点)

训练场里，原装 Lua Bone System 和 FirstNatives 各用十四类武器完成了装梅、切天狐、卸载，共 84 次。任务内另行核对了 FirstNatives 的废神社单人探索（太刀）和原装 Lua 的水没林普通狩猎（操虫棍）。水没林的三次切换耗时 2.72、3.81、3.00 秒，均从最后一个文件落盘计到目标资源可见，操虫棍和猎虫全程保留。[训练场与任务实测](docs/quest-equipment.md)

整套五件已确认穿在本地主控身上时，插件会一直按原猎人的挂点装配。防具部件或共享工厂仍在准备时，等它们就绪后再试。独立隐藏脸发、复杂头盔规则或关节层级不相容时，装配可能要等游戏下一次正常穿戴。单独改动部分装备、强制重置脚本时中断了 FirstNatives 影骨交接，有各自的兼容和恢复路径。[适用范围与实测](docs/worn-skeletons.md#原猎人的五个防具挂点)

1. 安装崛起版 REFramework。普通外观和 Lua Bone System 使用 REFramework 的 **LooseFileLoader**。使用 FirstNatives 时，关闭这个开关，让 FirstNatives 负责读取松散文件。使用 Lua Bone System 的玩家可以继续使用自己的 LuaBoneSystem.lua。热加载适配随本插件的 DLL 提供。从 1.0.0 升级时，先退出游戏，在 Fluffy 中停用旧版并结束之前手动运行的监听器。手动安装过旧版的玩家需先移出其 `MHRS_Files_HotReload.lua`、`MHRS_HotReload` 脚本目录和旧版的辅助程序。
2. 将 `MHRS-Files-HotReload-v1.1.0.zip` 拖入 Fluffy，在 **Monster Hunter Rise** 中启用。手动安装时，用包内的 `reframework/plugins/mhrs_hotreload.dll` 更新游戏里同名的 DLL。
3. 启动游戏，保存、安装或卸载 `natives/stm` 下的外观。DLL 在游戏进程内监听变动，记录写在 `reframework/data/MHRS-Files-HotReload/watcher.log`。日志中的 `Watching` 表示已取得启动基线。
4. 插件使用崛起的平台文件名读取运行后才放入的装备模型、材质及贴图。在 NTFS 上，它为松散原件临时创建同数据的 `.stm` 硬链接。卸载启动前就已装入的外观时，插件按本机 PAK 的补丁优先次序读取原件，验证后可暂存为独立的 `.stm` 副本，供本局再次创建装备。监听器正常停止时会清理插件拥有的条目。游戏进程先退出时，遗留条目在插件下次启动、采集基线前清理。发生路径冲突时保留其他模组的文件，日志记下冲突路径。

v1.0.0 安装包已用 Fluffy 在 Steam 版崛起实测。村内覆盖 279 装备的贴图后，角色身上出现了测试用的洋红色。新增、覆盖和删除水车动作文件时，同一水车的动作末帧依次为 239、119、89、239。279 腰甲约束在新增和覆盖后由 4 项变为 3 项、2 项，删除后在重建装备时恢复 4 项。

279 实穿、同编号换装、重建玩家、保留的预制体工厂和 18 类资源的逐项读数见[同路径替换与删除回退验收](docs/reentry-18.md)。荒野格式对应关系和既有的随机新路径实验见[冷加载对照](docs/wilds-parity.md)。

道具箱的单件外观预览会在小窗相机重新启用时校准渲染目标。关闭预览后再替换或删除资源，重新打开时，单件小窗与整身预览各自使用当前目标。

构建单 DLL 玩家包需要 Windows x64、Python 3.12、Git 和 Visual Studio C++ x64 工具链。运行 `python tools/build_player_package.py dist/MHRS-Files-HotReload-v1.1.0.zip`。构建脚本取用固定版本的静态 CPython SDK 和 REFramework 的 Lua 源码，将监听器、脚本及资源索引一并链接进 DLL。下文的 Python 命令供源码开发与历史用例复测，手动监听和玩家 DLL 应分别运行。

首次构建会将依赖缓存到 `native/build`。本地已有对应版本时，传入 `--python-sdk <已解压的SDK目录> --reframework-source <REFramework检出目录> --zstd-source <Zstandard 1.5.7源码目录>` 可离线构建。`--verify` 在独立宿主验证单 DLL 的启动、文件变更、PAK 回退与退出，`--verify-texture <TEX文件>` 可加入真实纹理样本。使用独立进程从源码读取 PAK 需要安装 `zstandard`，`--external-watcher` 构建这一对照版本另需 PyInstaller 6。

监听器优先使用 Windows 目录变更通知。游戏进程拒绝订阅父目录时，插件定期核对该目录，能订阅的子目录仍使用通知。预制体回收和已修改 HUD 的重新绑定分帧执行。旧版村内移动和训练场出招的测量见[性能对照](docs/performance.md)。

保存或删除文件后，监听器只更新引用发生变化的资源。给正在使用的资源换绑时，游戏可在下一帧推进已就绪的步骤。装备预览等界面暂未打开时，游戏会在对应节点就绪后通知监听器。村内水车从文件落盘到确认绑定的中位时间由 2.07 秒缩短到 1.04 秒。[保存延迟和跑图复测](docs/save-performance.md)

监听器按 `natives/stm` 下的资源路径识别正在穿戴的装备。换场期间，插件记录待刷新的资源路径，等新猎人的实穿部件就绪后按最后落盘的文件装配。1.0.6 在原猎人上替换部件。旧版本的整套模型重建记录保留作对照。[骨架和穿戴物理实机记录](docs/worn-skeletons.md) · [实际任务换装与队友判定](docs/quest-equipment.md)

1.0.5 支持在原猎人身上刷新单件装备的顶点位置。插件核对实际加载的文件与原版 MESH，仅在骨骼、权重、材质槽及索引一致、目标部件及其父子挂点没有 CHAIN、也没有该性别的松散影骨时，直接为已有渲染器换绑。改模型结构的整套外观继续使用游戏的装备装配流程。整套安装时平台文件可以并行准备；插件识别自己创建硬链接产生的文件变更，避免在目录通知溢出后重复刷新整套。[保留原猎人的实机记录](docs/worn-skeletons.md#在原猎人上换资源)

1.0.4 在原版 Lua Bone System 姿态修复 v2 和 FirstNatives 下分别实测了训练场全部 14 类武器，每类均完成原版 → 梅 → 天狐 → 原版。整套刷新沿用原有装备和 PlayerData，训练场实测有两个猎人内部计时器会重新初始化。任务内已实测废神社探索、水没林毒狗龙王、冰封群岛雪鬼兽。联机队友的完整外观目前等待游戏重建该队友的显示模型，两名真人同场尚待验证。[逐项实测和限制](docs/quest-equipment.md)

单独修改相容的 CHAIN 时，已有物理组件直接采用新组。单独修改 FirstNatives 的套装影骨时，插件检查当前穿戴的完整套装，把模型绑定到现有猎人，按关节核对实际基础姿态。对于已识别的 Lua Bone System 版本，本插件在 JSON 安装、修改或删除后更新对应的缓存，由原脚本在自己的动画阶段处理关节和 IK。ArmorVariantManager 的 JSON 仍由该前置自行管理。[早期 1.0.1 冷安装对照](docs/wilds-parity.md)

监听器随包识别 154,118 条原版逻辑路径，并读取 339 份原版材质模板的参数与贴图接口。删除同路径覆盖时，游戏从 PAK 读取替代资源。需要比较 GUI、PFB、USER 的原版字段，或读取未收录的模板原件时，可额外指定 `--baseline-root "<原版 natives/stm>"`。平台渲染目标保留游戏文件的完整后缀，例如 `PreviewCamera_Equip.rtex.5.stm`。

监听器查找 `natives/stm` 下的松散文件。单文件保存可以刷新正在使用的组件。日志中的 `Next use` 表示已改走下次创建时重新请求资源的路径。场景中暂时停用的组件重新激活并成功换绑时会打印 `Reactivated`。

修改 HUD 的 UVS 时，监听器更新实际使用它的纹理节点，保留界面的动画时间线。切换区域或重新打开界面后，已就绪的视图会使用当前图标。正在播放的特效通过 EffectPlayer 刷新。带流式高清层的纹理需要配套的 `streaming` 文件，游戏会按画面距离选择实际使用的 mip 层。

GUI、PFB 和 USER 在下一次创建时都读取整份资源。原地更新已有实例的兼容字段时，监听器使用启动时的松散文件或上次保存的内容计算差异。传入 `--baseline-root "<原版 natives/stm>"` 可以获得首次覆盖前的原件及包内依赖关系。指定 `--rsz-schema "<rszmhrise.json>"` 可启用单根标量 USER 的类型检查与实时写入。

如果游戏启动后才第一次把某个原版资源放到 `natives/stm`，LooseFileLoader 可能已缓存该路径没有松散文件的结果。实测腰甲在这种情况下仍读到原版 4 个约束输出。在 REFramework 的 **LooseFileLoader → Debug** 取消勾选 **Enable file cache** 后再次保存，腰甲立即读到松散文件的 11 个输出。监听器在绑定单组 JCNS 前会对照磁盘和新资源的输出数量，数量不符时回滚，保留原约束层。这项检查只比较数量。

材质刷新按槽名保留启用开关。磁盘默认值相同的布尔、浮点、四分量和贴图绑定可保留运行时取值，文件中已修改的参数采用新值。实穿手甲已核对同一个槽中一个运行时四分量保持不变、另一个四分量采用新默认值。预制体和 USER 引用的结构替换结果见[同路径验收](docs/reentry-18.md)。

## 整份手甲 MDF 热加载

验证环境为 Windows x64、Steam 16.0.2.0（Build 17920865）、REFramework v1.5.9.1+472-c4b13148。原生模块依赖此版游戏的内部布局与方法，并在运行时检查构建特征。

1. 这一节复现早期的开发者手动测试。在单独的开发安装中构建原生模块，部署相应的脚本与开发 DLL，启用 REFramework 的 LooseFileLoader。
2. 穿上使用目标 MDF 的手甲，在项目目录运行以下命令。监听器运行期间直接保存 `natives/stm/player/mod/f/pl279/f_arm279.mdf2.23`，按 Ctrl+C 结束监听。

```powershell
python tools/watch_arm279.py "F:\SteamLibrary\steamapps\common\MonsterHunterRise" --native
```

原生流程借鉴荒野版对旧资源生命周期、依赖就绪和当前 Mesh 绑定的处理。崛起的路径缓存使用有序树。模块在管理器的临界区内将旧对象暂存到另一个键，调用游戏自身的资源创建函数重新请求原路径。新 MDF、材质模板和贴图准备就绪后，脚本绑定新 holder，再释放事务引用。旧对象随现有使用者的引用正常释放。失败或依赖等待超时会尝试恢复原缓存条目。

实测只更改 `Meira_5_outer_Arm / BaseDielectricMap` 的贴图引用。手动和保存触发各完成一次 `moon_5.tex → moon_6.tex → moon_5.tex`。每次使用同一 Mesh 和原逻辑路径，MDF 对象地址随重载更新。对六个材质槽的 56 个贴图绑定逐项比较，只有目标引用变化。自动监听实测两次保存到绑定回执约 0.96 秒、0.84 秒，测试结束原文件 SHA-256 与基线一致。

首次引用新贴图时，只等待依赖就绪会导致超时。实测新纹理进入资源缓存后已完成第一阶段加载，第二阶段仍处于待处理状态。现行模块在游戏线程上调用崛起自身的资源初始化函数，确认纹理就绪后才绑定整份 MDF。在村内给当前手甲引用新路径的洋红色 BC7 sRGB 贴图，保存约 0.45 秒后观测到贴图文件打开，1.00 秒收到绑定回执。角色手甲的两圈白色毛边之间从深色变为洋红色。改回原件后约 0.86 秒收到回执，画面恢复深色，六槽的全部绑定及原文件哈希均恢复。以上结果针对该手甲、同一材质模板和槽布局。

编译可运行 `native/build.cmd`，需要 Visual Studio C++ x64 工具链。复测贴图前先退出监听器，再运行 `python tools/test_native_arm279.py "F:\SteamLibrary\steamapps\common\MonsterHunterRise"`。报告和备份保存在 `local-tests/native-<编号>/`。如果外部测试进程被强制终止，原件可从该目录恢复。

复测首次引用的新贴图时，保持原生监听器运行，并将其标准输出重定向到日志文件。另开终端运行 `python tools/test_cold_arm279.py "<游戏目录>" "<监听日志路径>"`。该测试需要上述自定义手甲和原贴图 `moon_5.tex.28`，会生成唯一命名的测试纹理，验证保存和恢复两次绑定，并在恢复后清理纹理。记录和原件保存在 `local-tests/cold-<编号>/`。

## 早期颜色刷新模式

将本仓库的整个 `reframework/autorun` 目录合并到游戏的同名目录，在 `reframework/data` 下创建 `MHRS-Files-HotReload` 目录，然后加载脚本。穿上使用 `f_arm279.mdf2.23` 的手甲，在修改 MDF 前从项目目录启动监听：

```powershell
python tools/watch_arm279.py "F:\SteamLibrary\steamapps\common\MonsterHunterRise"
```

看到 `Captured 12 bindings` 后可直接保存目标 MDF。监听器合并短时间内的文件变动，游戏线程通过 `via.io.file.copy` 读取原松散路径到自己的快照，解析 MDF2.23，按材质名和参数名更新手甲。按 Ctrl+C 结束监听。重新换装或重载脚本后，在再次修改文件前重新启动监听以采集当前手甲。

在已穿戴的同一只手甲上，`moon_RimColor` 的测试值覆盖了六个槽，延迟 8.61 秒读回仍为 (1, 0, 1, 1)。另一次仅保存文件的测试中，监听器约 0.25 秒后收到更新回执，六个槽采用新值；恢复原文件后，六槽及原 MDF 哈希均恢复。两个实验都沿用原 Mesh。当前另一个探测参数 `S_col_R` 在后续采样时回到了原有运行时值，其覆盖来源待定位。该颜色模式仅处理上述参数。

### 资源复用与荒野实现的对照

本机 REFramework 的 Lua 绑定把请求转交给游戏的 `via.ResourceManager`。在覆盖后，原路径请求返回的原生资源地址与已穿戴 Mesh 的材质 holder 所持地址相同；NTFS 通知在显式刷新读盘时触发。可观察到的复用边界是资源管理器的返回值。崛起反射暴露的管理器方法中未找到按路径清除或重载的入口。另一次只读实验中，在逻辑路径中加入 `./` 返回了不同对象，并在主动对照读取前触发同一物理文件的打开通知；该实验未绑定新对象。

荒野版会暂时移开旧缓存条目、按原路径加载，等待 MDF 和依赖就绪后提交，再刷新正在使用它的 Mesh，并按新旧文件差异保留运行时覆盖。崛起颜色原型沿用了按材质和参数比对的思路。此处的早期颜色实验保留了原资源对象；原生模式的实测见上节。[荒野加载与 Mesh 刷新实现](https://github.com/AleksKavil/MHWS-Files-HotReload/blob/e3ef3e067bfed2da5c1a1adac79c55fe1dbaaa08/src/hotreload.cpp) · [REFramework 资源管理器封装](https://github.com/praydog/REFramework/blob/c4b13148/shared/sdk/ResourceManager.cpp)

2026-11-14，Steam Build 17920865，游戏 16.0.2.0，REFramework v1.5.9.1+472-c4b13148。角色已穿戴使用 `player/mod/f/pl279/f_arm279.mdf2` 的手甲。测试期间保持装备和场景固定。

本次采样未观察到当前手甲立即采用新值。实验不能单独确定资源缓存、加载时序或其他插件分别起了什么作用。`S_col_R` 的运行时初值和文件初值已有差异，因此以上表格使用与原文件一致的 `moon_RimColor` 判断。

另一次异路径对照在绑定请求返回后游戏退出，未取得绑定后的样本。该分支已移出原型。测试工具已恢复原 MDF，恢复前后的原件 SHA-256 为 `23b026bb53abff3983a2a2142334d16a9d6f574026da35d3449d01577dec1e20`。

## 原路径请求的文件访问复测

在相同装备下原子替换目标 MDF，随后在新文件上申请 NTFS batch oplock。等待观察就绪后通过游戏内探针请求原资源路径并重新绑定。请求返回后继续观察 8.61 秒，六个槽在早、晚两次采样中都保持旧值。整个观察窗口内没有触发打开通知。随后测试工具主动读取同一文件，立即触发首次通知，读到的内容与修改版 SHA-256 完全一致。

在这次测试条件下，没有观察到引擎重新打开覆盖后的松散 MDF 读取新内容。此方法观察单个文件，不能定位具体缓存层。系统级 ETW 会话未获得管理员权限，本次使用文件级观测。原文件已按 SHA-256 核对恢复；旧版探针重新绑定保存的 holder 后，游戏在最后一次采样前退出。现行探针只请求资源并读取当前材质，已移除两个设置材质的调用。

移除材质绑定后，在村内对同一手甲单独执行 `sdk.create_resource`。调用返回了资源对象，之后 8.31 秒内未观察到覆盖后的 MDF 被重新打开。首次打开通知出现在测试工具主动读取文件时，读取内容与测试版哈希一致。两次采样中六个槽均保留初值。恢复后再次核对，原文件哈希、六个槽的名称、启用状态、`S_col_R` 和 `moon_RimColor` 均与覆盖前一致，游戏持续运行。

## 复测同路径覆盖

1. 按上面的安装步骤部署入口和 MDF 解析模块，启用 LooseFileLoader。启动游戏，或在 REFramework 的 ScriptRunner 面板点击 Reset scripts。单独运行验证程序前先退出监听器。
2. 在村内穿戴使用目标材质的手甲，保持装备和场景不变。此测试针对包含 `S_col_R`、`moon_RimColor` 两个四分量参数的自定义 `f_arm279.mdf2.23`。测试期间暂停对该源文件的其他编辑。
3. 在项目目录运行 `python tools/test_arm279.py "F:\SteamLibrary\steamapps\common\MonsterHunterRise" --observe-opens`，按实际安装位置替换路径。文件观察适用于本地 NTFS。工具会备份原件，生成测试颜色，原子替换目标文件，然后分别记录覆盖后、请求原资源后和恢复文件后的参数。观察结束时，工具主动读取目标文件，以校验通知及测试内容。
4. 原件备份及逐槽 JSON 记录位于 `local-tests/<本次测试编号>/`。如测试进程被强制中断，可从该目录把 MDF 复制回 `natives/stm/player/mod/f/pl279/`。
5. 在上述验证命令后追加 `--refresh` 可测试显式读取原 MDF 并刷新手甲颜色。
